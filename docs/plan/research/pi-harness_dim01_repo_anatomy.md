## A. UI rendering pipeline — how phase/cycle/evaluator state reaches the TUI

**Two parallel UI systems exist:**

1. **`src/dashboard.ts`** (run-state UI):
   - `updateStatusBar(ctx, state)` → `ctx.ui.setStatus("iterative-goal", …)`: `🎯 C{cycle} {phaseIcon} {phase} · {progress}% · {evalInfo}`. Progress = `calculateProgress()` = `min(95, (cycle-1)*100/(cycle+2))` — **cycle-only heuristic; ignores phase and taskPlan**.
   - `updateWidget(ctx, state)` → `ctx.ui.setWidget("iterative-goal", lines, { placement: "belowEditor" })`: goal, `C{cycle} {icon} {phase} · {status}`, last verdict + next focus, ≤2 completion blockers, ≤2 unresolved errors.
   - `DashboardComponent` (modal via `ctx.ui.custom`, opened by `/goal-dashboard`): shows status, goal, cycle/phase, evaluator (`lastVerdict` else `evaluatorState.status` else "not started"), artifact counts R/P/I/V/Eval, last 5 errors, verdict blockers/remaining work. **Static snapshot** — state captured at construction; `invalidate()` exists but is never invoked on state change.
2. **`src/harness-ui.ts`** (startup/harness UI, registered by `registerHarnessUi`):
   - Fires **only on `session_start` and `model_select`** → `renderStartupUi()` sets `setTitle`, `setStatus("iterative-goal-harness", …)` (`ig {mode} · {model} · subagents:{kind} · goal C{cycle}/{phase}`), `setWidget("iterative-goal-startup", …, { placement: "aboveEditor" })`, and `setHeader(() => new HarnessHeader(...))` which renders `goal: C{cycle} {phase} {status}`. **All captured state goes stale immediately after session start** (`HarnessHeader.invalidate() {}` is a no-op).
   - Commands: `/harness-dashboard` (static `HarnessDashboard` modal), `/harness-doctor`, `/harness-mode`, `/security-review-status`, `/security-review-start`.

**Refresh mechanism — purely imperative, transition-triggered.** `updateStatusBar`/`updateWidget` are called from: `kernel/lifecycle.ts` `advanceToNextPhase()` (after `setPhase`), `handleValidateTransition()` (post-verdict, on all four outcome paths), the synthetic-failure pause path, and `session_start` restore; and from `ui/goal-commands.ts` handlers (`goal-start/status/pause/resume/approve/deny/repair-capabilities`, `goal-reset` → `clearStatusBar`). Verified: **no `setInterval` anywhere in `src/`** (search, 0 matches); StateManager has no subscribe/notify; `startPhaseAttempt()` (`kernel/workflow-engine.ts`) does not touch UI.

**GAPS for "cleanly rendering the phase the goal is presently in":**
- **G1 — Stale always-visible header:** the `HarnessHeader` (the most prominent phase display) refreshes only on session_start/model_select, so it shows the wrong phase for the entire run.
- **G2 — No in-phase liveness:** phase is only repainted at transition boundaries. `lock.phaseStartedAt` / `PhaseAttempt.startedAt` exist but no elapsed-time/heartbeat render; no spinner during long phases.
- **G3 — Evaluator running state invisible in status bar/widget:** `evaluatorState` (`queued|running|passed|failed|error|stale_heartbeat`, heartbeat in `evaluator.ts → updateEvaluatorHeartbeat`) is shown only in the modal dashboard and `/goal-status --json`; `updateStatusBar`/`updateWidget` read only `lastVerdict`.
- **G4 — Task plan not surfaced in chrome:** in-progress `TaskPlanItem` appears in `latest.md`, `/goal-status`, and prompts, but not in status bar/widget; `goal_update_task_plan` triggers no UI refresh.
- **G5 — No progress granularity:** progress % ignores the 4-phase cycle position and shard/task completion.
- **G6 — Dual UI ownership:** `dashboard.ts` ("iterative-goal") and `harness-ui.ts` ("iterative-goal-harness"/"iterative-goal-startup") duplicate the goal/phase line with different freshness; neither has an event subscription — the natural fix is one phase-indicator module driven by StateManager events (event ledger already exists, see D).

## B. Swarm substrate — `goal_subagent` today

**`src/subagents.ts → registerGoalSubagentTool`:** params `{ agent?, role?, task, allowedPaths?, model?, mode?, cwd? }`. Role enum (10): Scout, Requirements analyst, Planner, Implementer, Test engineer, Security reviewer, Architecture/Ousterhout advisor, Documentation reviewer, Release reviewer, Integrator. Execution path: writer roles (Implementer/Integrator) hard-require `allowedPaths` (else policy block); if `commandExists("pi")` is false → returns `"[SUBAGENT BACKEND: NONE]"` single-agent-fallback text (`details.fallback=true, result="single-agent-fallback"`). Otherwise builds one `AgentTask` via `createAgentTask` (budget `maxTurns:4, maxTokens:16000, timeoutMs:300_000` = `constraints.subagentTimeoutMs`), `workspace: "isolated_worktree"` for writers else `"read_only_snapshot"`, then routes through `CapabilityBroker.invoke` (PolicyEngine gate, effect `process.exec`) into `new PiSubprocessAgentPool(cwd).submit(task)`.

**What it cannot do today (gaps for parallel specialist fan-out):**
- **S1 — `mode` is dead schema:** `"single"|"parallel"|"chain"` accepted but **never read** in `execute()`. No fan-out exists at the tool surface.
- **S2 — Parallel primitive exists but is unwired:** `agents/pool.ts → AgentPool.map(tasks, { concurrency })` (default 2) and `cancel(taskId)` are implemented but **never called**; a fresh pool is created per tool call and discarded.
- **S3 — DAG fields unused:** `AgentTask.dependsOn: string[]` and `inputArtifactIds: string[]` exist but nothing consumes them — no scheduler.
- **S4 — Backend detection is advisory only:** `detectSubagentBackend()` (capabilities.ts) can return `{kind:"tool", toolName:"subagent"|"Agent"}` or command backends, but `execute()` only ever uses the pi-subprocess pool; detected tool backends are never invoked.
- **S5 — No cross-call coordination:** write-scope conflict detection (`findWriteScopeConflict`/`pathsOverlap`, glob-prefix conservative) works only within one pool instance = one call; no shared writer registry, no cancellation surface for operator/model.
- **S6 — No ledger/UI integration:** subagent runs emit no events into `events.jsonl`, no artifacts, no TUI progress (a swarm call blocks one agent turn up to 5 min). Result patches from isolated worktrees are appended to output text as `[ISOLATED_WORKTREE_PATCH]` but **no apply/merge-back step exists**.
- Role strings in `harness-ui.ts` ("scout/planner/worker/reviewer/oracle", "context-builder") are display literals that don't match the real `AgentRole` enum.

## C. Sharding attach points

**What the plan phase produces today:** free-text `PhaseArtifact` (persisted to `cycles/<n>/plan/result.json`) + the durable task checklist `state.taskPlan` via `goal_update_task_plan` (`ui/tools.ts`): full-list replacement, items `{id, title, status: pending|in_progress|completed|blocked|cancelled, detail, evidence[], updatedAt}`, enforced unique ids and ≤1 `in_progress`, DLP/IPI scrubbed, recorded to `task-plan.jsonl` + `task_plan_updated` event. `phases.ts → renderPlanPrompt` instructs "Call goal_update_task_plan with the bounded checklist for this cycle. Keep exactly zero or one item in_progress" and demands an exact-files allowlist; `renderImplementPrompt` says "Execute exactly ONE bounded slice". The evaluator (`evaluator.ts`, unfinishedTasks check) **blocks goal completion while any task item is pending/in_progress/blocked** — a shard-aware gate must preserve this.

**Latent shard schema (major finding):** `src/domain/plan.ts` exports `PlanSpecSchema { id, version, tasks[], createdAt }` and `PlanTaskSchema { id, title, dependsOn[], satisfies[], allowedPaths: PathScope[], requiredCapabilities[], checks: VerificationSpec[], rollback, risk: low|medium|high }` — a shard-ready typed plan model. Code search confirms `PlanSpecSchema` is **referenced nowhere else in the repo** — defined but completely unwired. Only `extractAcceptedAmendmentScopes` (typed `PlanAmendment` JSON blocks, status-gated) is used, by `workspace/change-set.ts`.

**Natural seams for a post-research+plan sharder/scheduler:**
1. **`kernel/lifecycle.ts → advanceToNextPhase()`** — the exact plan→implement transition (calls `stateNextPhase`, `setPhase`, then `startPhaseAttempt` + prompt). A sharder hook fits after the plan artifact commits in the `agent_end` handler (mirror of the existing `if (state.phase === "implement") verifyImplementationAgainstPlan` special-case).
2. **`ui/tools.ts → goal_update_task_plan` handler** — fires when the plan phase writes the checklist (`TaskPlanState.updatedByPhaseAttemptId` identifies the plan attempt).
3. **Data seam:** derive shards either from `state.taskPlan.items` (flat) or by parsing `state.artifacts.plans.at(-1).content` into the latent `PlanSpecSchema`; per-shard path scopes reuse `domain/path-scope.ts` (already used for allowlist verification in `workspace/change-set.ts → verifyImplementationAgainstPlan`).
**Worktree isolation:** does **NOT** exist in `src/workspace/` (only change-set.ts diff verification) nor in `src/git.ts` (only status/checkout_branch/add/commit/push/create_pr via `goal_git`, policy+ReleaseAuthorization-gated). It exists **only in `src/agents/pool.ts → prepareIsolatedWorktree()`**: `git worktree add --detach` into `os.tmpdir()`, `capturePatch()` = `git diff --binary`, cleanup via `git worktree remove --force` + process-exit cleanup registry. Missing for sharding: patch apply/merge-back, a persistent cross-task write-scope lease registry, and shard→worktree lifetime management. Docs confirm `/goal-finalize --mode isolated-worktree` is "stubbed but not implemented" (context_001/002 reports). `policy/engine.ts` already has the gating vocabulary: `Effect` union (fs.*, process.exec, git.*, cloud.*, …), `ActionRequest.taskId?`, and `PolicyDecision.lease?: CapabilityLease { runId, taskId?, effect, resource, maxUses, expiresAt }` — lease plumbing anticipates per-shard scoping.

## D. State/event ledger — blackboard fit

`src/state.ts → createStateManager(pi)` (factory; `StateManagerAPI`). Run dir `.pi/iterative-goal/runs/<runId>/` with **`events.jsonl` = authoritative, append-only, hash-chained ledger** (`appendEvent` adds `sequence`, `previousEventHash`, `eventHash` = sha256; `verifyEventHashChain` rejects tamper → replay fails closed). Full event sourcing: `replayEvents()` rebuilds state via a `replayHandlers` table; `restore()` prefers replay, falls back to `state.json` snapshot, then to session-level `pi.appendEntry("iterative-goal-state", envelope)` (survives compaction). Event types: `run_created` (embeds `initialState`), `phase_attempt_started/completed`, `artifact_recorded`, `verdict_recorded`, `error_recorded`, `status_changed`, `phase_changed`, `cycle_incremented`, `lock_acquired/released`, `queued_phases_cancelled`, `evaluator_state_updated`, `release_authorization_updated`, `task_plan_updated`, `dlp_state_updated`, `sanitizer_state_updated`, `attestation_recorded`, `approval_requested/resolved`, `capabilities_updated`, `project_instructions_updated`, `goal_met`, `completed_external_blockers`, and `phase_lifecycle` (audit-only wrapper for the 17 `PhaseEventKind`s incl. `phase_started`, `evaluator_queued/started/verdict_recorded`, `transition_decided`, `next_phase_started`, `stale_phase_output_ignored`). Side ledgers: `evaluator-verdicts.jsonl`, `approvals.jsonl`, `attestations.jsonl`, `dlp-redactions.jsonl`, `task-plan.jsonl`; per-phase artifact dirs `cycles/<n>/<phase>/` (result.json, diff.patch, implementation-verification.json, final.patch). Audit surface: `/goal-audit`, `/goal-replay`, `/goal-trace` (`ui/commands.ts`).

**Blackboard verdict:** strong substrate — append-only verified log + replay-handler table is exactly where `shard_posted / shard_claimed / shard_result / subagent_started / subagent_finished` event types would be added (plus replay handlers and state fields). Missing today: no claim/lease events, no producer/consumer artifact addressing (artifacts are per-phase append-only arrays), and **no pub/sub** — consumers (UI, schedulers) cannot watch the log; everything is imperative pull.
